Which pages are quietly losing search visibility — and which one should an editor open first?

Youssef Abozaid Refresh / Content Opportunity Scoring 2026-08-02 Repo →
Abstract. Content editors can't manually re-check thousands of pages a month, so pages that are quietly declining in search visibility often go unnoticed. Using one month of FlyRank's search-performance warehouse, a page-level feature set was built from prior-window signals only (impressions, position, clicks, sessions), and a declining-visibility label was defined from a later window that was never fed into the model. A logistic regression model, evaluated on a client-holdout split against a transparent baseline rule, reached 0.700 precision in its top-50 ranked picks — above the 0.680 baseline and clearly above the 0.224 base rate — giving editors a directional, decision-support queue to work from each week.

01Introduction

The problem this supports

A FlyRank content editor manages far more pages than they can manually audit in a given week. The decision this work supports is simple to state and hard to do by hand: which pages should be reviewed for a refresh this week, and why?

Unit of analysis: one content page, scored once per month. Output: a ranked list with a decline-risk score and a plain-language reason code. A wrong call has a real cost either way — a false alarm wastes an editor's hour, and a missed one lets a page keep losing visibility for another month unnoticed.

02Data

FlyRank internship warehouse, one mid-panel month

This work uses the pseudonymized FlyRank warehouse release (v20260703) hosted on Hugging Face — specifically fact_content_daily_performance, filtered to month = '2026-03', a mid-panel month chosen deliberately over the most recent month (which is a sealed evaluation window for any past→future label).

Excluded on purpose

The warehouse's own trend_direction and trend_pct columns are exactly how the label in this work is defined — using them as features would mean feeding the model its own answer. They are excluded everywhere. Pseudonymous client and content IDs are used only to group the train/test split, never as inputs.

No client names, domains, URLs, or raw exports appear anywhere in this work — only pseudonymous hash identifiers used for grouping.

03Methodology

Past-only features, a held-out label window

The analysis month is split in half. The prior half supplies every feature; the later half supplies the label only. A page is labeled declining if its total impressions fell from the prior half to the later half — an observed outcome, not a hand-written rule.

Features — five, all knowable before the label window: average prior impressions, average prior search position, average prior GA4 sessions, average prior clicks, and how many days of data the page had in the prior window.

Baseline — a transparent rule computed the same way the model's features are: percentage drop in impressions between two sub-windows of the prior half. Not a shortcut through the label.

Models — logistic regression (transparent, coefficients read directly) and random forest (a non-linear comparison), both trained with class weighting for the 22.4% minority "declining" rate.

Validation — a client-holdout split: whole clients assigned to train or test, never split within a client, so the model is judged on clients it has never seen. 39 clients trained on, 13 held out, zero overlap.

An honest, unexpected result

Random Forest wins on overall discrimination (ROC-AUC) but loses to the baseline on the metric that actually matters here — precision in the top 50. Class-balancing spreads its confidence broadly across the minority class, which helps its AUC but doesn't concentrate correctly at the very top of the ranking. Since editors only ever work a short list, precision at the top decided the model choice: logistic regression is what's deployed, not the model with the higher AUC.

Recent impressions and search position do almost all of the work — engagement data (GA4 sessions) added comparatively little in this window, and prior clicks carried a mildly negative relationship with decline risk in the logistic model, plausibly because high-click-through pages simply have less headroom left to grow.

05Limitations

  • Not causal. Nothing here proves a refresh will improve a page's performance — only that a pattern was observed in past data.
  • Not a claim about Google's algorithm. The label is built entirely from FlyRank's own metrics.
  • One month, one snapshot. Seasonal effects and shifts in the client mix aren't represented.
  • Uneven history. Clients differ widely in how much prior data they have, which lowers confidence for thin-history pages specifically (flagged in Section 6).
  • A proxy label. "Declining impressions" is a proxy for "needs review" — a page can lose impressions for reasons that have nothing to do with content quality, like seasonality.

06Ranked recommendations

The action playbook

Each week, the top-50 scored pages become an editor's queue, tagged with a reason so the fix is obvious before they even open the page:

  • position problem — position is weak, impressions are still reasonable → rewrite / on-page work.
  • visibility problem — impressions themselves are low or falling, position stable → consider a merge or deeper review.
  • mixed signal — no clear pattern → needs a human look first.

Pages with fewer than 5 days of prior data are separately marked low-confidence and should be weighted accordingly, not trusted at face value — see the error analysis in Section 4.

07Reproducibility

Clone the repo, install dependencies, open the capstone notebook in Colab, set an HF_TOKEN secret, and run top to bottom:

git clone https://github.com/youssefabozaidyou/flyrank-ml-internship
cd flyrank-ml-internship
pip install -r requirements.txt
# then open work/notebooks/capstone.ipynb in Colab, Runtime → Run all
